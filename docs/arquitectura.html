1Decisiones clave

Respuesta corta

Sí: un solo backend NestJS en la nube, una sola API REST versionada y una sola base PostgreSQL sirven a la web y a la app mobile. No hace falta un backend por cliente ni microservicios. La modularidad que pide RNF-05 se resuelve con un monolito modular (un módulo NestJS por historia de usuario), que un desarrollador solo puede mantener y que se puede partir en servicios más adelante sin rehacer el modelo.

2Arquitectura lógica

Tres capas: clientes, API y datos. Los dos clientes hablan únicamente con la API por HTTPS y se autentican con el ID token que emite Firebase. La API verifica ese token, resuelve el comercio y el rol del usuario, y recién entonces toca la base. Los servicios externos (correo, LLM) se consumen sólo desde la API, nunca desde los clientes.

Por qué monolito modular y no microservicios

  • Un desarrollador, un despliegue. Cada módulo NestJS (productos, movimientos, proveedores…) tiene su controlador, servicio y repositorio; se prueban y documentan por separado (RNF-07) pero corren en un proceso.
  • Transacciones simples. Registrar una venta descuenta stock y crea el movimiento en una única transacción de PostgreSQL. Con servicios separados eso exige sagas o colas.
  • Camino de crecimiento. Si un módulo necesita escalar solo (por ejemplo el asistente de IA), se extrae detrás del mismo contrato OpenAPI. RNF-05 queda satisfecho por diseño, no por infraestructura anticipada.

4Multi-tenencia y seguridad

El tenant es el Comercio (Propuesta §2.3). Se adopta el modelo base única, esquema único, fila discriminada: cada tabla de negocio lleva comercio_id. Es el modelo más barato de operar para cientos de comercios pequeños y el que mejor se lleva con Prisma. El aislamiento (RNF-10) se garantiza en dos capas, para que un error de programación no alcance para filtrar datos entre comercios.

Capa 1 · Contexto de tenant en la API

Cada request pasa por una cadena de guards. El orden importa: primero se sabe quién es, después a qué comercio pertenece, después qué puede hacer.

// prisma/tenant.extension.ts — todo modelo con comercio_id se filtra solo
export const tenantPrisma = (comercioId: string) =>
  prisma.$extends({
    query: {
      $allModels: {
        async $allOperations({ model, operation, args, query }) {
          if (TENANT_MODELS.has(model)) {
            if (operation.startsWith('find') || operation === 'count')
              args.where = { ...args.where, comercioId };
            if (operation === 'create')
              args.data = { ...args.data, comercioId };
          }
          return query(args);
        },
      },
    },
  });

Capa 2 · Row Level Security en PostgreSQL

Defensa en profundidad: aunque una consulta olvide el filtro, la base no devuelve filas de otro comercio. La API abre cada transacción con set_config('app.comercio_id', …, true) y las políticas comparan contra ese valor. Dos detalles aprendidos al implementarlo (change auth-tenancy): el propietario de las tablas en Neon tiene BYPASSRLS, así que la API se conecta con un rol propio app_api sin ese privilegio y las migraciones siguen corriendo como propietaria; y el alta del comercio, que ocurre antes de que exista el tenant, usa una política de sistema (app.rol_sistema = 'provisioning') acotada a esa transacción.

ALTER TABLE producto ENABLE ROW LEVEL SECURITY;
ALTER TABLE producto FORCE ROW LEVEL SECURITY;
CREATE POLICY producto_tenant ON producto
  USING (comercio_id = app_comercio_actual())
  WITH CHECK (comercio_id = app_comercio_actual());
CREATE POLICY producto_sistema ON producto
  USING (app_es_sistema()) WITH CHECK (app_es_sistema());
-- la misma política se repite en movimiento, proveedor, gasto, alerta, orden_compra (docs/runbooks/rls.md)

Otras medidas de RNF-03

  • Cifrado: TLS en tránsito (Vercel, Render y Neon lo dan por defecto); cifrado en reposo del proveedor de base de datos. No se guardan contraseñas: las gestiona Firebase.
  • Superficie: helmet, CORS restringido a los orígenes de la web y la app, rate limit por IP y por comercio, tamaño máximo de archivo en la importación (5.000 filas, según wireframe).
  • Auditoría mínima: cada movimiento guarda usuario_id y fecha. Los movimientos no se borran (RN-07); una corrección es un ajuste que referencia al original.
  • Prueba obligatoria de aislamiento: un test e2e crea dos comercios y verifica que ningún endpoint del catálogo devuelva datos cruzados. Es la evidencia de RNF-10 para la cátedra.

Convenciones del contrato

  • Paginación por cursor en listados (?cursor&limit), pensada para el scroll de la app mobile.
  • Errores con forma fija { code, message, details }, mensaje en español apto para mostrar al usuario (RNF-01, RNF-08).
  • Montos en pesos como decimal(14,2) en la base y string en JSON, nunca float. Fechas en ISO 8601; períodos y reportes en zona America/Argentina/Buenos_Aires.
  • Campos sensibles (costo, margen) se omiten en la respuesta para el rol Empleado mediante un interceptor, no con un endpoint aparte.
  • Idempotencia en POST /movements con header Idempotency-Key, para que un reintento desde el celular no duplique una venta.
